## 8. Re-import of the chunked OVA through Forklift - FAILED, as documented (virt-v2v#189)

Provider `ova-big` (`<nfs-server-ip>:/ova-big/vm-import-ui-exports`) parsed the OVA fine (VM, disk and network listed; Plan `Ready`).
Migration failed in `ConvertGuest` with:

```
virt-v2v: error: inspection could not detect the source guest (or physical machine) operating system.
No root device found in this operating system image.
```

Cause, from the conversion pod log (virt-v2v 2.7.7): it tests for `disk-0.vmdk` (absent), then for `disk-0.vmdk.000000001`
(the highest-numbered chunk) and maps only that one, at tar offset 8589940736 with size 2947727360. Chunk 0, which holds the partition table and
boot sector, is dropped. This is libguestfs/virt-v2v#189 (fix proposed in #193). The OVA itself is valid (section 7).

## 11. Redo of the chunked-OVA tests on one clean artifact (posted to virt-v2v PR #193)

Why a redo: the first 20 GiB source was a CDI *smart clone* of `labs/ubuntu-2404`. That disk's StorageClass is image-backed (`backingImage: vmi-...`) and the clone's
class (`harvester-1replica`) is not, so the restore dropped the backing-image layer: the clone's `/boot` (p16) failed `e2fsck` (invalid resize inode, bad HTREE, corrupted root dir)
while the original passed, 24 of 100 hashed chunks differed and 9 of those were all zeros in the clone. The OVA was a faithful copy of the (damaged) clone, so it was not an exporter bug.
Not the random tail either: p16 sits at sectors 227328-2097152, the random data starts at 10 GiB, and e2fsck ran on the partition, not the raw disk.
Fix: clone with `cdi.kubevirt.io/cloneType: copy` (host-assisted, reads the full data); both partitions then pass `e2fsck -f -n` (`/boot` 600/58496 files, identical to the original).

One artifact, all results: 20 GiB source (clean Ubuntu 24.04 + 10 GiB random at offset 10 GiB), export `bigdisk-export.ova` 11,528,456,192 bytes,
VMDK 11,528,448,512 bytes in chunks 8,589,934,080 (2^33 - 512) + 2,938,514,432. The local copy needed per-range verified transfer (`kubectl exec cat` truncates large streams); final sha256 matches the server's.

| Check | Result |
|---|---|
| Stock virt-v2v 2.7.7 (Harvester image, in-cluster Job), `-i ova` | maps only chunk 1 (`offset 8589940736, size 2938514432`), `No root device found` (virt-v2v#189) |
| Patched virt-v2v (PR #193, 2.13.5), `-i ova -o null` | `presenting chunked disk disk-0.vmdk as 2 extents without copying`; `e2fsck` passes on /dev/sda16 and /dev/sda1; inspection identifies Ubuntu 24.04.4 LTS |
| Descriptor virt-v2v generated | `RW 16777215 FLAT ... 12` and `RW 5739286 FLAT ... 16777228` (matches the tar layout) |
| Byte-exactness | flat view opened as VMDK, `qemu-img compare` vs the source volume (20 GiB): **Images are identical** |
| Control | second extent shifted one sector: compare fails with a read error |

Correction to section 9: the "1 MiB temp space" row was measured after virt-v2v had exited (it removes its temp dir), so it proved nothing; evidence for the no-copy path is the log line and the descriptor source.
Comment posted: https://github.com/libguestfs/virt-v2v/pull/193#issuecomment-5922791394 (the local `resolv.conf` conversion failure, unrelated to chunking, was left out at the user's request).

## 10. Release verification on the cluster: v1.9.1 and v1.9.2

**v1.9.1 (export records kept until deleted).** `helm upgrade --reuse-values` to chart 0.3.1 left the pod on `EXPORT_TTL_SECONDS=3600`:
`--reuse-values` reuses the previous release's computed values, including the OLD chart's default. `--reset-then-reuse-values` gave `EXPORT_TTL_SECONDS=0`
with the user overrides (export enabled, NFS storage) preserved. A fresh export of `labs/ubuntu-2404` then had no `ttlSecondsAfterFinished` on its Job and stayed in the API list (`phase: Ready`).

**Bug found: purge for exports in other namespaces.** `DELETE .../exports/labs/<id>?purge=true` returned 200 and deleted the Job, but the OVA and `.vm-import-ui/<id>` stayed on the `labs` volume.
Cause: `DeleteExportHandler` removed files under the API pod's own `EXPORT_ROOT` without checking `exportVolumeMountedHere` (the pod mounts only its own namespace's volume),
so it also could have deleted a same-named OVA on the pod's own volume. Fixed in v1.9.2 (PR #10): purge removes files in-process only when the volume is mounted here; otherwise a
`vm-export-cleanup-<id>` Job runs in the export's namespace; the export Job is kept if cleanup cannot be scheduled.

**v1.9.2 verification** (chart 0.3.2, image 1.9.2, `--reset-then-reuse-values`): a decoy `purge-test.ova` was planted on the API pod's own volume (namespace `vm-import-ui`), then
`labs/ubuntu-2404` was exported with target `purge-test` and purged through the API.

| Check | Result |
|---|---|

| Cleanup Job in `labs` | succeeded; log `Removed export <id> (purge-test.ova) from /export` |
| `labs` export volume | OVA and `.vm-import-ui/<id>` both gone; two older status folders untouched |
